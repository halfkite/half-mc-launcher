# 二、多分栏与标签系统：更精确的规则

这一部分必须在正式开发前定好，否则会出现切换布局丢失标签、跨栏复制状态错误、固定标签被覆盖等问题。

## 2.1 一个分栏就是一个完整页面环境

每个 Pane 都包含：

```
Pane
├── TabBar
│   ├── Tab 1
│   ├── Tab 2
│   ├── ...
│   ├── 新建标签 +
│   └── 复制当前标签
│
├── PageHost
│   └── 当前完整功能页面
│
├── NavigationHistory
├── SearchAndFilterState
├── ScrollAndSelectionState
└── PaneFocusState
```

没有主分栏、副分栏或缩略页面的概念。

例如四个 Pane 可以全部打开实例列表，但分别查看：

- 第一个栏：所有实例。
- 第二个栏：只显示 Fabric 实例。
- 第三个栏：只显示开发测试分组。
- 第四个栏：查看外部磁盘中的实例。

四个栏都使用完整实例页面，且搜索和滚动状态各自独立。

当窗口太窄，无法同时以合理宽度显示四个完整页面时，应保证页面控件完整、允许局部滚动或工作区滚动，而不是偷偷删掉实例操作。可设置建议最小 Pane 宽度 280px、高度 200px。

## 2.2 标签创建与复制

| 操作       | 具体结果                       |
| -------- | -------------------------- |
| 点击 `+`   | 在当前分栏创建「实例」标签              |
| 点击复制图标   | 复制当前标签的页面类型、筛选、搜索与可序列化状态   |
| 点击标签 `×` | 仅关闭这个标签                    |
| 点击标签     | 切换当前显示页面                   |
| 拖动标签     | 在同栏排序或移动到其他栏               |
| 双击标签     | 可配置为重命名自定义标题或不执行操作         |
| 右键标签     | 复制、固定、移动到其他栏、关闭其他标签、关闭右侧标签 |

复制标签不得复制磁盘上的实例、重复下载任务或复制正在运行的 Java 进程。

关闭当前分栏的最后一个标签时，自动生成一个新的实例标签，该 Pane 不消失。

## 2.3 跨栏拖动

标签开始拖动后，目标分栏显示插入位置。

放下后需要保证：

1. 原标签 ID 和页面状态不变。
2. 目标栏获得该标签的实际所有权。
3. 源栏将标签移除。
4. 分栏焦点切换到目标栏。
5. 若页面正在执行下载、备份等任务，任务不因标签移动而中断。
6. 如果跨栏转移失败，标签仍保留在源栏。
7. 工作区自动保存变更后的状态。

不应通过关闭旧页面、创建新页面的方式粗暴模拟拖动。需要把页面状态与它的视觉承载控件分离。

## 2.4 五种布局切换如何保证不丢标签

推荐工作区内部始终管理最多四个稳定的 Pane ID，显示布局决定当前哪几个 Pane 可见。

例如四栏切换成左右双栏：

- Pane 1、Pane 2 继续显示。
- Pane 3、Pane 4 的标签可以临时显示在指定可见栏中。
- 内部仍记录这些标签原本属于 Pane 3、Pane 4。
- 切回四栏时自动恢复。
- 如果用户主动移动某个临时标签，则更新它的真实归属。

这要求建立「真实标签归属」和「当前显示位置」两套独立数据，不能仅靠一个列表保存。

还要支持临时最大化当前 Pane。最大化只改变可见布局，不修改用户保存的五种布局模式。

## 2.5 工作区保存与恢复

程序默认恢复上次退出状态。应保存：

- 窗口大小、位置、最大化状态。
- 左侧导航栏宽度与折叠状态。
- 分栏布局、分隔比例和聚焦栏。
- 每栏标签顺序、激活标签和固定状态。
- 每个标签的页面类型、搜索、筛选、分组、滚动位置和选择状态。
- 当前账户 ID。
- 当前工作区预设关联。
- 可恢复的页面参数，例如正在查看哪个实例。

不自动恢复已经结束的游戏进程，也不自动继续需要用户确认的危险文件操作。

工作区状态和命名预设是两种独立数据：上次会话负责还原，工作区预设负责快速切换。

### 3.2 实例四个直接操作

悬停时，卡片右侧直接显示：

&#x20;启动 设置 目录 删除

启动： 直接使用该实例当前账户和配置发起游戏启动。若检测到必须处理的问题，才弹出修复或错误提示。

设置： 打开完整实例设置页面，可以选择在当前栏的新标签中打开。

目录： 左键直接在 Windows 资源管理器打开游戏目录；按钮右侧下拉区域提供 `mods`、`config`、`saves`、`resourcepacks`、`shaderpacks`、`logs` 和 `screenshots` 快捷入口。

删除： 一定打开确认窗口。提供仅从列表移除、删除实例专属文件两种方式，并明确显示受影响的磁盘路径。真实删除还要经过第二次确认。

屏幕较窄时，这四个按钮可以自动排列成两行，但不能藏进原来的三个小点菜单。

## 3.3 多文件夹管理

「管理目录」打开独立的完整管理页面。

顶部可添加扫描目录，列表展示每个目录的路径、扫描深度、扫描状态、上次扫描时间、找到的实例数量和排除规则。

建议支持以下扫描策略：

| 策略              | 说明                             |
| --------------- | ------------------------------ |
| 标准 Minecraft 目录 | 解析 `.minecraft/versions` 和启动配置 |
| 独立实例集合          | 搜索每个子目录中的有效实例配置                |
| 第三方启动器目录        | 用相应格式适配器导入                     |
| 手动指定实例          | 对非标准目录指定游戏版本和入口                |
| 自动监控变动          | 新增或删除实例时更新索引                   |
| 排除目录            | 忽略备份、临时目录和指定路径                 |

版本定义和实际游戏实例必须分开处理。

一个版本可能对应多个使用不同游戏目录的配置；不能扫描到 `versions` 下的文件夹就假定它一定是完整、独立的实例。

扫描时建议按照文件路径归一化、实例格式识别、元数据验证、实例身份去重、信息更新的顺序进行。发现同一个实例被两个扫描根目录覆盖时，合并其来源关联，而不是显示两个副本。

已有目录默认采用保守管理策略：

- 不自动修改原始启动器配置。
- 不复制或迁移原文件。
- 不自动删除已经失联的实例。
- 不自动安装缺失模组。
- 修改、迁移和删除时明确显示影响范围。

如果移动硬盘断开，实例显示「路径不可用」，并提供重新定位，而不是把它视为已删除。

- 显示文件大小。

- 显示是否存在缺失前置。
- 显示磁盘总占用。

依赖树支持两个方向：

- 正向查询： 当前模组需要哪些前置？
- 反向查询： 禁用当前模组会影响哪些模组？

关系图不应简单地采用树形结构，因为多个模组可以共享前置，还可能存在循环关系和重复节点。

建议使用有向图数据结构，提供缩放、搜索、关系过滤、选中节点高亮以及「查看所有间接依赖者」。

同时标记关系来源，例如加载器元数据、下载平台、用户配置或静态推测。未经过确认的联动关系不能标记成强制前置。

# 六、二分法排障：算法和交互细化

这是目前规划中最需要认真设计的功能之一。

## 6.1 进入排障前

用户进入「实例 → 模组管理 → 智能排障」时，先显示准备页面。

准备页面应让用户设置：

| 选项   | 说明                    |
| ---- | --------------------- |
| 排查实例 | 默认当前实例                |
| 故障类型 | 启动崩溃、进入世界崩溃、功能异常、性能异常 |
| 测试环境 | 默认隔离临时实例              |
| 锁定模组 | 用户指定始终启用的模组           |
| 自动启动 | 每轮准备完成后是否自动启动测试       |
| 测试结果 | 自动识别或用户手动判断           |
| 快照保护 | 默认启用且不可绕过关键检查         |
| 测试数据 | 选择是否复制存档和必要配置         |

必须首先确认原始故障可以复现。

例如一个故障只在特定世界内出现，那么仅仅判断游戏能不能打开主菜单是不够的。需要让用户选择正确的故障复现方式。

## 6.2 核心算法

建议排障时维护三个集合：

```
B = 始终保留的基础模组

C = 当前待排查模组

T = 本轮实际启用的模组
```

每轮从 `C` 中选择一部分模组进行测试，生成满足依赖约束的 `T`。

最简单的单模组故障场景：

```
原始 64 个模组
        ↓
测试 32 个
        ↓
测试 16 个
        ↓
测试 8 个
        ↓
测试 4 个
        ↓
测试 2 个
        ↓
测试 1 个
```

但实际实现要允许测试「保留半组」和「排除半组」这两种互补集合。

### 核心决策规则

| 测试结果      | 下一步                |
| --------- | ------------------ |
| 故障依然出现    | 优先缩小到仍能复现故障的集合     |
| 故障消失      | 在满足单一、稳定故障假设时检查另一半 |
| 缺少前置，无法启动 | 该轮无效，重新组合依赖集合      |
| 结果不稳定     | 保留多个候选，重试或转入高级排障   |
| 只在两组组合时出现 | 转入组合冲突最小化测试        |
| 只有完整集合复现  | 不再强行二分，输出限制说明和测试报告 |

对涉及多个模组共同触发的问题，应尝试 `ddmin` 一类的最小化策略，而不能保证固定六轮就找到根因。

## 6.3 保护真实实例

排障系统建议设计 `BisectSession` 独立会话。

```
BisectSession
├── SessionId
├── SourceInstanceId
├── OriginalManifest
├── LockedMods
├── CandidateMods
├── DependencyGraph
├── CurrentRound
├── TrialInstancePath
├── TestHistory
├── ReproductionRule
└── RecoveryState
```

排障过程中：

1. 保存原始模组列表和哈希。
2. 创建临时测试目录。
3. 按当前轮次放入需要启用的模组。
4. 复制必要的配置和测试数据。
5. 启动独立测试环境。
6. 获取日志、退出码和用户判断。
7. 保存每轮结果。
8. 计算下一轮。
9. 最终生成报告并清理临时资源。

临时测试环境可以共享不可变的 Java 运行时或下载缓存，但不能把需要写入的存档、配置文件直接与原实例共享。

不建议对可写数据简单使用硬链接，否则测试游戏可能直接改变原文件。

## 6.4 排障结果页面

最终结果不只是输出一个模组名称。

建议包含：

- 最小可复现候选集合。
- 可疑模组和依赖关系。
- 各轮测试组合。
- 每轮日志。
- 用户判断记录。
- 已尝试的组合数量。
- 是否验证通过。
- 下一步建议。
- 导出完整排障报告。
- 恢复原实例状态。

如果问题无法唯一定位，需要明确展示「未确定根因」，不能强行猜测。

只负责 Minecraft 游戏内部设置预设。

每套预设支持如下数据：

| 分类  | 内容                   |
| --- | -------------------- |
| 画面  | 渲染距离、模拟距离、帧率、同步、画面选项 |

### 预设字段必须具有三态

这是防止应用预设时覆盖过多设置的关键。

一个设置字段应该能够表达：

- 不修改目标实例现有值。
- 应用预设指定的值。
- 显式恢复为该 Minecraft 版本所定义的默认值。

不能用 `null` 同时表示「不修改」和「恢复默认」。

### 资源包与光影的应用

游戏预设中的资源包和光影应保存为资源引用加校验信息，而不是依赖某个临时下载路径。

应用时先检查文件是否存在、校验哈希、确认版本兼容，并使用适配器更新目标实例的相关配置。

光影选项尤其需要考虑 Iris 等不同加载器的配置格式。不能把一种加载器的启用配置无条件应用到另一种加载器。

### 服务器列表

支持合并、只添加缺失项、完全替换三种模式。

默认选择合并，并对目标实例原有的 `servers.dat` 做备份。服务器地址相同但名称或其他属性不同的条目，应当显示冲突处理窗口。

## 7.3 实例设置

这是针对某一个实例的配置页。

它可以使用全局默认值，也可以拥有独立覆盖项。

推荐优先级为：

实例独立覆盖配置

优先级最高

已绑定的默认游戏设置预设

仅影响勾选应用的类别与字段

实例原有游戏设置

没有明确覆盖时保留

默认游戏设置的页面内可直接选择目标实例批量应用。

而在下载游戏、创建实例时，也需要有「默认游戏设置」选择区：

```
创建 Minecraft 实例
├── 版本选择
├── 加载器选择
├── 实例名称与目录
├── Java 与内存
├── 正版账户
├── 默认游戏设置
│   ├── [✓] 启用预设
│   ├── 预设：日常生存
│   └── 选择应用类别
└── 开始创建
```

实例创建完成、必要文件安装成功后，再应用已选择的默认设置。

批量应用必须提供差异预览。

例如：

| 实例          | 当前视距 | 预设视距 | 结果 |
| ----------- | ---- | ---- | -- |
| Fabric 生存   | 16   | 12   | 调整 |
| 原版测试        | 8    | 12   | 调整 |
| NeoForge 测试 | 12   | 12   | 保持 |

遇到不支持的配置项，应跳过并报告，而不是写入无效配置。实例正在运行时，将文件修改安排到安全时机。

# 八、正版账户与皮肤管理

账户栏位于左下角，独立于当前分栏。

展开侧边栏时：

```

## 8.1 账户列表功能

每个账户显示头像、昵称、登录状态、最近使用时间。

- 一键打开 Minecraft 官方个人资料页面。
- 一键打开官方兑换 CDK 页面。
- 一键打开正版账户管理页面。

账户令牌加密保存，不能暴露给普通插件。

# 九、下载游戏与下载资源

## 9.1 下载游戏

负责创建可启动的 Minecraft 实例。

页面包含游戏版本筛选、正式版/快照筛选、加载器选择、安装目录、Java 配置、账户和默认游戏设置。

安装流程为：

```
选择版本
  ↓
选择加载器
  ↓
确认实例名称和目录
  ↓
选择 Java / 账户 / 游戏设置预设
  ↓

  ↓

  ↓

  ↓

## 9.2 下载资源

建议把资源分成模组、资源包、光影、整合包、数据包等类别。

需要允许用户在一个资源页面中选择多个实例批量安装。

这里能够与多分栏很好地结合：一个分栏显示资源详情，另一个分栏显示实例列表，拖动资源到实例卡片上即可进入安装确认流程。

# 十、全局任务中心与进度动画

整个程序只应有一个全局任务调度器，不允许每个标签各自管理独立下载线程而互不知情。

建议的任务状态：

| 状态   | 说明             |
| ---- | -------------- |
| 等待中  | 等待并发槽位或资源锁     |
| 准备中  | 校验输入、计算依赖、确定路径 |
| 运行中  | 下载、安装、扫描或备份    |
| 暂停   | 支持暂停的任务才可进入    |
| 等待确认 | 需要用户处理覆盖或冲突    |
| 成功   | 完成并通过验证        |
| 失败   | 保存错误原因         |
| 已取消  | 清理或保留可恢复的中间数据  |

每个任务拥有自己的详情页面、子任务进度、日志和错误信息。

例如游戏下载进度可以显示：

```
Minecraft 1.21.1 安装任务

✓ 获取版本元数据
✓ 检查 Java
✓ 下载游戏 JAR
● 下载依赖库
○ 下载 Assets
○ 验证文件
○ 创建实例

当前文件：library-example.jar
已下载：128 MB / 350 MB
速度：8.2 MB/s
```

上面的数值仅为布局示例。真实进度必须来自已知任务和下载字节数，不能通过模拟定时增长来假装正在工作。

关闭任务详情标签不取消任务。

对于程序更新、实例备份等操作，若执行中途关闭程序，应保存恢复状态，并在下次打开时提供恢复或清理入口。

# 十二、插件平台的更完整接口

插件 SDK 不只是支持注册一个页面，还要能够在不破坏主程序的情况下扩展资源下载、实例识别和自动化。

建议将插件能力分成五层。

| 层级    | 扩展接口                                          | 权限范围        |
| ----- | --------------------------------------------- | ----------- |
| 页面扩展  | `IPageProvider`、`INavigationProvider`         | 注册完整页面与导航   |
| 实例扩展  | `IInstanceProvider`、`IInstanceActionProvider` | 读取实例、添加实例操作 |
| 下载扩展  | `IResourceProvider`、`IGameInstaller`          | 资源搜索和安装     |
| 诊断扩展  | `IModMetadataProvider`、`IDiagnosticProvider`  | 解析依赖、生成检测结果 |
| 自动化扩展 | `ICommandProvider`、`IWorkflowProvider`        | 命令、事件与工作流   |

另外要提供 `ISettingsAdapter`，专门让插件注册特殊模组配置适配器。

例如某插件可以实现一个特定模组的配置读取和预设应用能力，而不需要修改主程序中的默认游戏设置模块。

## 插件生命周期

至少包含：

```
发现插件
  ↓
验证清单与兼容性
  ↓
检查启用状态
  ↓
加载插件
  ↓
注册服务和页面
  ↓
运行
  ↓
禁用或退出
  ↓
清理资源
```

普通 .NET DLL 在启动器主进程中执行时，不具备强安全隔离。因此应将可信进程内扩展与独立进程插件宿主分开设计。

插件不能直接取得账户原始令牌；涉及游戏目录修改的请求，应通过启动器统一的文件服务提交和审计。

插件缺失时，其原有标签应显示「插件不可用」页面，而不是直接丢弃工作区状态。

## 13.3 默认游戏设置模型

```
public enum SettingAction

    KeepExisting,
    SetValue,
    ResetToDefault
}

public sealed class PresetSetting<T>
{
    public SettingAction Action { get; set; }

    public T? Value { get; set; }
}
```

这样每个预设字段可以明确表达「不改」「设置」「恢复默认」。

还应为每一套预设保存 `PresetId`、版本号、名称、类别、资源引用、兼容条件和更新时间。

# 十四、界面动画与细节标准

动画需要统一，而不是每个页面随意定义。

| 场景     | 动画            | 建议时长  |
| ------ | ------------- | ----- |
| 切换标签   | 内容淡入          | 120ms |
| 新建标签   | 横向展开          | 160ms |
| 关闭标签   | 收缩、后续标签补位     | 140ms |
| 实例悬停   | 操作按钮渐显        | 120ms |
| 左侧栏折叠  | 宽度渐变，文字淡出     | 180ms |
| 布局切换   | 分栏平滑缩放        | 220ms |
| 工作区切换  | 保存旧状态、淡入新布局   | 180ms |
| 拖动标签   | 跟随鼠标及插入位置提示   | 实时    |
| 启动完成   | 进度状态转为完成状态    | 200ms |
| 文件操作失败 | 显示明确错误，不只播放震动 | 即时    |

上述时间是 UI 设计目标，不是实际测量结果。

必须提供「减少动画」设置，支持跟随 Windows 系统偏好。

# 十五、功能开发优先级重新安排

不建议为了追求功能数量而一次性把所有模块同时写完。应该先把底层做好，再按里程碑逐步接入。

| 阶段       | 核心交付                | 完成后能做什么            |
| -------- | ------------------- | ------------------ |
| M1 工作区   | 窗口、侧栏、五布局、标签、状态恢复   | 完整操作多分栏界面          |
| M2 实例管理  | 多目录识别、分组、搜索、操作保护    | 管理现有 Minecraft 文件夹 |
| M3 启动引擎  | 正版登录、Java、版本解析、游戏启动 | 真正启动已安装的游戏         |
| M4 下载与预设 | 游戏下载、模组安装、默认游戏设置    | 创建实例、配置游戏、安装资源     |
| M5 模组与诊断 | 模组树、二分排障、快照、操作历史    | 检测、排查并修复模组问题       |
| M6 插件与工具 | SDK、插件管理、开发者工具、CLI  | 第三方扩展及自动化          |
| M7 发行质量  | 更新、迁移、主题、性能、回归测试    | 稳定发布与升级            |

### 第一版可运行程序的验收目标

在 M1 完成时，至少要求：

- 侧边栏可拖动，并根据宽度自动折叠。
- 顶部全局操作全部位于单行标题栏。
- 五种分栏布局能够切换。
- 每个分栏拥有完整、独立的页面。
- 标签能创建、复制、关闭、固定和跨栏移动。
- 点击侧栏模块，只影响当前聚焦分栏。
- 关闭并重新打开程序后，恢复原来的窗口、布局、侧栏宽度与所有标签。
- 数据默认保存到启动器程序目录。
- 如果配置损坏，能够恢复上一份有效工作区快照。
- 插件页面注册接口可以被独立测试。

### M2 完成时增加的验收目标

可以添加多个游戏目录，扫描到实际实例并显示完整信息；支持实例搜索、分组、收藏和快捷打开目录；删除有二次确认；直接导入的旧游戏文件不被扫描器修改；磁盘失联不导致实例数据丢失。

### M5 完成时增加的验收目标

模组树正确展示声明依赖和反向依赖；二分排障能够保存并恢复测试会话；单模组可复现故障可以通过逐轮缩小定位候选；组合冲突能够进入高级排障；文件修改失败可以执行恢复流程；批量应用游戏设置不会无条件覆盖未选中的设置。

# 十六、特别容易遗漏的边界情况

最后建议把这些也正式写进开发规格：

| 特殊情况          | 应有处理              |
| ------------- | ----------------- |
| 四栏切双栏再切四栏     | 原标签和页面状态完整恢复      |
| 同一个实例出现在四个分栏  | 实例数据共享，页面状态独立     |
| 两个分栏同时更新同一实例  | 实例写入锁阻止文件冲突       |
| 实例目录处于不可用磁盘   | 显示失联，支持重新定位       |
| 运行游戏时批量应用预设   | 暂缓修改，提示退出后执行      |
| 预设的资源包文件丢失    | 提示重新定位或恢复资源       |
| 模组二分造成缺少前置    | 标记本轮测试无效，不误判      |
| 插件卸载后仍有插件标签   | 显示插件不可用页面         |
| 程序升级后旧工作区格式变化 | 先备份再迁移            |
| 复制启动器目录到新盘符   | 内部相对路径自动继续生效      |
| 程序目录不可写       | 让用户选择路径，不擅自写入 C 盘 |
| 删除实例时目录被共享    | 阻止危险删除并说明受影响实例    |
| 下载中断或校验失败     | 保留可恢复任务并清理不可信文件   |
| 游戏崩溃时仍在保存存档   | 避免立即覆盖，保留诊断信息     |

## V3.3 最终架构划分

WinUI 3 Application Shell

单行标题栏 · 侧栏 · 账户 · 全局状态

Workspace + Pane + Tab

五种布局 · 完整页面 · 跨栏拖动 · 会话恢复

实例与游戏启动

默认游戏设置

模组诊断与备份

下载和任务管理

Core Services + Plugin SDK

实例索引 · 文件事务 · 数据存储 · 插件接口

便携式数据目录

配置 · 工作区 · 实例索引 · 预设 · 缓存 · 日志

现在这份 V3.3 规格已经把主要功能从「要做什么」细化到「页面怎么组织、操作怎样执行、数据如何保存、失败怎样恢复」。

下一步正式进入编码时，我建议首先固定三个可作为契约的模块：WorkspaceManager 的布局树和标签状态模型、InstanceDiscoveryService 的多目录识别协议、InstanceMutationService 的安全文件修改协议。这三者决定了绝大多数后续功能能否稳定扩展。
